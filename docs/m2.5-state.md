# M2.5 — On-disk state and peer identity persistence

**Status:** Design note, 2026-04-20. Sits between M2 (rendezvous works) and M3 (signed handshake).

---

## The problem we uncovered

Running `ultranet serve` twice in a row produces **the same peer id**. That surprised me, and it matters.

What's happening: arti defaults its state directory to `~/.local/share/arti/` on Linux. That directory holds the hidden-service keypair indexed by nickname. Because `publish()` always uses the nickname `"ultranet-m2"`, arti finds the existing key file on the second run, reuses it, and produces the same `.onion` address.

Two consequences:

1. **The M2 design doc claimed ephemeral identity. That claim is false in practice.** The hidden-service ed25519 private key is sitting in a file at `~/.local/share/arti/keystore/...` right now, in plaintext.
2. **Invariant I2 ("no plaintext identifiers on disk") is violated** — not because we wrote careless code, but because we let a dependency's default behavior silently contradict our stated guarantees. This is exactly the kind of drift the design system is supposed to catch early.

This is a small problem right now (one keypair, one dev machine, no real users). It is a huge problem if we ship and forget about it.

---

## What we will and will not do at M2.5

### M2.5a — land now, small code change
**Force ephemeral state by default.** Both `bootstrap()` and `publish()` will use a per-process temporary directory for arti's state, created fresh and deleted on exit. This makes the "ephemeral identity" claim honest: every `serve` generates a new peer id; every `dial` builds a new set of guard circuits.

This is not the long-term answer, but it's the honest near-term answer. It also makes the code match what our docs say *today*, which matters more than the elegance of any specific future design.

### M2.5b — design now, implement when needed
**Passphrase-encrypted persistent state.** When a user opts in (say `ultranet serve --persistent`), we:

1. Prompt for a passphrase at startup.
2. Derive a 256-bit root key with **Argon2id** (tuned so a wrong guess takes ~1 second on target hardware).
3. Encrypt the on-disk state directory contents with **XChaCha20-Poly1305**, chunked at the file level.
4. Decrypt into a tmpfs-backed RAM directory at startup, which is what arti actually reads.
5. Re-encrypt and sync back on clean shutdown; the tmpfs copy vanishes on process exit.

Threat model implications (cross-ref `docs/02-threat-model.md`):
- **T7 (physical seizure):** an attacker who seizes a powered-off device cannot recover state without the passphrase.
- **T7, powered-on:** the decrypted tmpfs copy is in RAM; a live forensic attacker still has access. Full mitigation requires the full TPM/SEV-SNP story (M2.5c / Track 2).
- **T10 (rubber-hose):** out of scope for the protocol; supported at L5 via decoy passphrases, a later feature.

We **design it now** (this section), but we **do not implement it until a persona needs it**. No current workflow in `03-personas.md` is blocked by ephemeral identity — they're blocked by not having the network at all. When M3 or M4 introduces a workflow where identity *must* survive across restarts, we turn on M2.5b as a single coherent change.

### M2.5c — long-term, Track 2 only
**TPM sealing.** On sealed-appliance hardware (Track 2), the root key comes from a TPM that wipes on chassis intrusion. The same `KeyStore` interface we design for M2.5b plugs into a TPM-backed implementation at M2.5c. The software-fortress nodes (Track 1) use passphrase-encrypted Argon2 as the default; sealed appliances use TPM.

## Shared interface across the three tiers

The thing that has to be right for this to compose cleanly is the interface. One trait, three implementations over time.

```rust
/// Provides the 32-byte root key used to encrypt all on-disk state.
pub trait RootKey {
    fn bytes(&self) -> &[u8; 32];
}

/// Strategies that can produce a root key.
pub enum RootKeySource {
    Ephemeral,                                 // tier 0 — M2.5a — tmpdir wiped on exit
    Passphrase { prompt: String },             // tier 1 — M2.5b — Argon2id
    OsKeyring { service: &'static str },       // tier 1.5 — convenience
    Tpm { index: u32 },                        // tier 2 — M2.5c — Track 2 hardware
}
```

M2.5a ships only `RootKeySource::Ephemeral`. M2.5b adds the others. The rest of the code doesn't change between tiers.

## What actually changes in code for M2.5a

Very little:

1. `ultranet-transport::bootstrap()` — accept an optional state-dir path; when absent, create a `tempfile::TempDir` and pass it into `TorClientConfig`. Hold the `TempDir` inside the returned client handle so it stays alive for the client's lifetime.
2. `ultranet-rendezvous::publish()` — no direct change; inherits the ephemeral state dir from the client.
3. One new dependency: `tempfile`.
4. On the listener side, `serve` now prints a new peer id every run. Document that in the `--help` text.

Estimated code: ~30 lines. No new crates. No API surface changes above transport.

---

## Out of scope for M2.5

- **Actually implementing passphrase encryption.** That's M2.5b; waits until a workflow demands it.
- **Encrypting arti's cache files (relay descriptors, consensus).** These are public information anyway — every Tor user has them. No I2 concern.
- **Secure memory allocation (mlock, zeroize on drop).** Useful eventually, out of scope for M2.5a.
- **Key rotation policy.** With ephemeral mode, rotation is automatic on every restart. Structured rotation for persistent mode is part of M2.5b.

---

## Ready?

M2.5a is the one concrete change: switch to a tempdir-backed state directory, so ephemeral identity is actually ephemeral. Fifteen minutes of work. Then M3.
